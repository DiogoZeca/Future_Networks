# M4 — Robustez e testes

> *"Idle timeout, clean handling of abrupt disconnects and bad JSON, Ctrl+C
> shutdown that closes sockets, logging, automated tests with pytest"* —
> slide 123

**Objetivo:** que nenhuma forma de uma ligação morrer (ou de um cliente se
portar mal) deixe o servidor num estado errado; que o servidor saia do Ctrl+C
limpo; que se perceba pelo log o que aconteceu a cada ligação; e que tudo
isto se prove com testes automáticos que qualquer pessoa corre com um comando.

### P38 — UTF-8 inválido (como o pytest o encontrou)

O teste de fuzz manda 500 linhas de lixo e espera 500 × `ERROR 400`. Falhou
de uma forma inesperada: **o próprio teste rebentou** com `UnicodeDecodeError`
no `json.loads()`. Uma das linhas era `{"type":"MSG","text":"\xc3\x28\xff"}` —
JSON sintaticamente válido, mas com bytes que não são UTF-8. O cJSON não
valida o encoding, o servidor aceitou-o (`OK`) e reenviou o `CHAT` a toda a
gente. O nosso cliente em C mostrava os bytes; **um cliente em Python
rebentava** — ou seja, um grupo podia derrubar os clientes Python dos outros
com uma mensagem. O RFC 8259 (§8.1) diz que JSON trocado entre sistemas TEM de
ser UTF-8; agora a linha inteira é validada antes do parse (estrito: sem
*overlong*, sem *surrogates*, nada acima de U+10FFFF).

### P39 — Porque é que fechar "normalmente" gerava RST

Quando a aplicação faz `close()` com bytes do peer ainda no buffer de
receção, o kernel (RFC 1122 §4.2.2.13) manda **RST** em vez de FIN — e o RST
faz o kernel do outro lado deitar fora o que ainda não foi lido, incluindo a
nossa última resposta. Isto acontecia exatamente quando fechávamos por culpa do
cliente: a linha de 70 KB (o resto ainda a chegar) ou o `QUIT` seguido de mais
dados. O `linger_drain()` faz o fecho em dois tempos: `shutdown(SHUT_WR)` (o
FIN sai **depois** do que já está no buffer de envio) e ler e deitar fora até
o cliente fechar também — então o `close()` já não tem nada por ler. Com um
prazo (2 s), para um cliente que nunca feche não prender a thread.

## As decisões do M4

Continuam a numeração do M3 (D13–D22). O estado de cada uma está no
`PROTOCOL.md`; o que parte se divergirem, no `DECISIONS.md` (secção D).

| # | Decisão | O que escolhemos | Porquê | No código |
|---|---|---|---|---|
| D23 | Inatividade | **300 s** sem **mensagem** (linha completa) → `ERROR 408 "idle timeout"` e fecho; antes do `NICK`, **30 s desde a ligação** → `408 "nick timeout"` | 300 s e 408 são os do grupo 1; o prazo antes do `NICK` é interno (só afeta quem não entra) e protege os 64 lugares; contar **linhas** e não bytes impede manter a ligação viva com 1 byte de 299 em 299 s | `serve()`, `session_timeout()` |
| D24 | Encerramento | `EVENT "server shutting down"` a cada ligação, FIN, sair com 0; sem `"x left"` | `EVENT` qualquer cliente mostra; `ERROR` seria "pedido recusado" sem pedido nenhum | `session_shutdown()`, `serve()` |
| D25 | Keepalive do nosso cliente | `LIST` silencioso se não enviou nada há **120 s**; sem `USERS` durante mais 120 s → o servidor morreu | sem tipos novos (D2: um `PING` seria `unknown type` nos outros servidores); 120 < 300 dá margem; um só parâmetro (`-k`) para os dois prazos | `keepalive_thread()` |
| D26 | Fecho do nosso lado | `linger_drain()`: FIN + ler até o cliente fechar, no máx. 2 s (1 s no encerramento, 200 ms no 503) | P39 | `net.c` |
| D27 | Log | stderr, uma linha por evento, `INFO` por omissão; o texto das mensagens só em `DEBUG` | o log diz quem e porquê, não o quê | `log.c` |

*Alternativas consideradas:*

- **D23:** `SO_RCVTIMEO` no socket (por chamada, como o `SO_SNDTIMEO` que o M2
  rejeitou: um cliente que mande 1 byte de vez em quando renovava-o); TCP
  keepalive (`SO_KEEPALIVE`) — só apanha a máquina morta, não o cliente vivo e
  calado, e os parâmetros são específicos de Linux; um `PING`/`PONG` (tipo
  novo, a acordar com todos os grupos).
- **D24:** `ERROR 503 "server shutting down"`: um código que o cliente podia
  tratar, mas "ERROR" quer dizer "pedido recusado".
- **D25:** sem keepalive (o utilizador calado era desligado ao fim de 5 min);
  uma linha vazia (o nosso servidor salta-a e não conta como mensagem — nem
  devia, D23).
- **Acordar as threads no Ctrl+C:** `shutdown(SHUT_RDWR)` a cada socket a
  partir da thread principal (precisava de percorrer o roster e não deixava a
  thread avisar o seu cliente antes); `pthread_kill` (sinais a threads:
  frágil). O pipe que todas vigiam é uma linha em cada `poll()`.

## Arquitetura (o que mudou no servidor)

```
  main:  poll(listener, stop_pipe) ─► accept() ─► thread (sinais bloqueados)
              ▲                                        │
     Ctrl+C ──┤ on_stop(): stopping=1; write(stop_pipe)│
              │                                        ▼
  por cliente:  wait_readable(fd, stop_pipe, prazo) ──┬─► bytes   ─► recv ─► rxbuf ─► session ─► deliver
                                                      ├─► prazo   ─► ERROR 408 ──────────────┐
                                                      ├─► stop    ─► EVENT shutting down ────┤
                                                      └─► QUIT / 413 ────────────────────────┤
                                                                                              ▼
                       roster_remove ─► "x left" (não no encerramento) ─► linger_drain ─► client_release ─► thread_done
  main (encerramento): fechar o listener ─► esperar nthreads == 0 (máx. 7 s) ─► roster_destroy ─► exit 0
```

com o log num ficheiro; e no fim de cada teste **encerra-o com Ctrl+C** e

fugas de memória.

```sh
make pytest                                   # tudo

python3 -m pytest tests/system/test_interop.py --host <ip> --port 5000   # outro grupo
```

## Como reproduzir

```sh
make && make test SAN=1 && make pytest

./bin/server -v -i 20 5000         # log com DEBUG, inatividade de 20 s
./bin/client 127.0.0.1 5000 ana    # noutro terminal
```

O que experimentar à mão:

- `nc 127.0.0.1 5000` e não escrever nada → ao fim de 30 s, `408 nick timeout`.
- Com `-i 20`, um `nc` com `NICK` e calado → `408 idle timeout` ao fim de 20 s; o
  nosso cliente (keepalive de 120 s) com `./bin/client -k 5 ...` nunca cai.
- Ctrl+C no servidor → cada cliente mostra `* server shutting down` e sai; o
  log acaba em `encerrado: todas as ligacoes fechadas`; `./bin/server 5000`
  logo a seguir arranca (sem *address already in use*).
- Ctrl+C no cliente → os outros veem `* ana left`; no log do servidor,
  `(ana) saiu: QUIT`.
- `kill -STOP` ao servidor (simula a máquina morta) com um cliente `-k 2` → o
  cliente avisa `o servidor nao responde` e sai; `kill -CONT` depois.
- `printf '{"type":"MSG","text":"\xff"}\n'` por `nc` depois de um `NICK` → `400 invalid JSON`.

## Notas / o que aprendi

> **Saber dizer isto sem ler é o objetivo** — são as perguntas prováveis na
> defesa.

### 1. "E se um computador se desligar?" — as quatro mortes, agora todas tratadas

| Como morre | O que o servidor vê | Desde |
|---|---|---|
| Fecha normalmente | `recv() == 0` (FIN) | M0 |
| Processo morto, ou fecho com dados por ler | `ECONNRESET` (RST) | M0 |
| Não lê (Ctrl+Z, portátil a dormir com tráfego) | o envio não acaba em 5 s | M2 |
| **Cabo arrancado, sem bateria, Wi-Fi caído** | **nada** — só o silêncio | **M4**: 300 s sem mensagens → 408 |

A última é a que não se resolve com `recv()`: não há FIN nem RST porque a
máquina não teve oportunidade de os mandar. O TCP keepalive do kernel só atua
ao fim de 2 horas. Por isso o prazo é da aplicação — e por isso o nosso
cliente manda keepalives: senão um utilizador só a ler seria tratado como
morto.

### 2. Porque é que o prazo conta mensagens e não bytes

Se contasse bytes, um cliente podia manter a ligação (e um dos 64 lugares)
mandando 1 byte de 299 em 299 s, sem nunca completar uma linha. Contando
linhas, a única forma de ficar é falar o protocolo. E antes do `NICK` o
prazo nem sequer é renovado: quem ainda não entrou tem 30 s, ponto.

### 3. O *self-pipe trick* (e porque é que a 1.ª versão falhou sob o TSan)

Um handler de sinal só pode fazer quase nada (funções *async-signal-safe*:
não pode usar `printf`, `malloc`, mutexes). O truque: o handler escreve um
byte num pipe; o resto do programa espera por **fds** com `poll()`, e o pipe é
mais um fd. Assim o sinal transforma-se num acontecimento como outro qualquer,
tratado no código normal. A 1.ª versão usava `pselect()` (desbloqueia os
sinais só durante a espera) — correto, mas o ThreadSanitizer só entrega os
sinais nas funções que interceta, e o `pselect()` não é uma delas: o Ctrl+C
esperava pela ligação seguinte (P44). Bónus do pipe: um byte que ninguém lê
deixa-o legível para sempre, e **todas** as threads o veem no seu `poll()` —
acordar 64 threads é escrever 1 byte.

### 4. Porque é que fechar com `close()` pode perder a última mensagem (P39)

Ver acima. A frase para a defesa: *"um close() com dados por ler manda RST, e
o RST faz o outro lado deitar fora o que ainda não leu — incluindo a nossa
última resposta; por isso fechamos em dois tempos: shutdown(SHUT_WR) e ler até
ao FIN do outro lado"*.

### 5. Porque é que o Ctrl+C espera pelas threads

As threads são *detached* (ninguém faz `join`), mas usam o roster. Se o
`main()` chamasse `roster_destroy()` (ou simplesmente saísse a libertar coisas)
com threads vivas, era um *use-after-free*. Um contador protegido por um mutex
e uma condvar diz quando a última acabou. O prazo (7 s) cobre o pior caso de
uma thread: um envio a meio para um cliente que não lê (5 s) + o linger (1 s).

### 6. Porque é que o fuzz valeu a pena (P38)

Os testes que escrevemos à mão testam o que nos lembrámos de testar. O fuzz
mandou combinações em que não pensámos — e a primeira falha nem foi no
servidor, foi no cliente Python **do próprio teste**: exatamente o que
aconteceria ao cliente de outro grupo. Usa uma semente fixa (`Random(4)`):
o "aleatório" é sempre o mesmo, por isso uma falha reproduz-se.

### 7. Um teste que passa com o bug não testa nada (mutação 9)

O teste "lixo não renova o prazo do `NICK`" começou por verificar só que o
408 chegava. Com a mutação (o lixo renova o prazo) o 408 chegava na mesma —
mais tarde. O teste passou a medir **quando** chega (< 1,6 s com `-n 1`). É a
segunda vez (depois da mutação 5 do M3) que um teste novo só ficou bom depois
de ser posto à prova com o bug.

### 8. `exit()` numa thread pode nunca terminar (P46)

```c
static void *t(void *a) { sleep(1); exit(0); }      /* outra thread */
int main(void) {
    pthread_t th; pthread_create(&th, NULL, t, NULL);
    char buf[100];
    fgets(buf, sizeof buf, stdin);   /* espera, COM o lock do FILE stdin */
}
```

Com o stdin num pipe que ninguém escreve: na glibc 2.35 (Ubuntu 22.04) o
programa sai; na 2.39 (Ubuntu 24.04) **fica pendurado para sempre**. O
`exit()` despeja todos os `FILE` abertos, e as glibc recentes passaram a
**trancar** cada um antes de o despejar (bug 15142 da glibc: sem o lock, o
despejo corria ao mesmo tempo que outra thread a escrever). Só que o
`fgets()` da thread principal tem o lock do `stdin` enquanto espera — e
espera para sempre. O nosso cliente fazia exatamente isto quando o servidor
fechava (a thread de leitura chamava `exit()`), e no modo terminal não se
via porque aí o teclado é lido com `read()`, sem `FILE`. A correção:
`term_exit()` repõe o terminal e despeja à mão só o stdout e o stderr (que
ninguém tem trancados), e sai com `_exit()`, que não toca nos `FILE`.

A lição: **testar noutra máquina não é uma formalidade.** Os 98 testes
passavam todos, com ASan e TSan, numa só máquina.

### 9. Porque é que os testes de sistema são em Python (e não em C)

Pelo slide, e por uma razão melhor: são **um cliente que não escrevemos em C,
noutra linguagem, com outra biblioteca de sockets** — como os dos outros
grupos. O P38 só apareceu por isso. E em Python há armadilhas que convém
conhecer: um socket sem referência é fechado logo (um `join("ana")` sem
guardar o resultado faz a ana sair a meio do teste), e `sock.close()` não
fecha enquanto houver um `makefile()` aberto (M3, nota 10).
