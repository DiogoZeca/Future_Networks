## O que muda em relação ao M1

| | M1 | M2 |
|---|---|---|
| Servidor | **iterativo**: um cliente de cada vez | **uma thread por cliente** |
| 2.º cliente | handshake TCP feito, nunca servido | servido de imediato |
| Uma mensagem | uma resposta, para quem a enviou | 1 ou 2 saídas, cada uma com **destino** |
| Estado partilhado | nenhum | `struct roster` — e com ele todos os bugs de concorrência |
| Cliente | pedido-resposta | **duas threads**: teclado e socket |
| Tipos | NICK, MSG, OK, CHAT, ERROR | + **EVENT** |
| Testes | 4 suites | + `roster` (incl. 3 de concorrência) + TSan |

## As quatro decisões do M2

### D7 — Tempo de vida: contagem de referências

**O problema.** O broadcast tem de enviar **fora** do lock: com o lock agarrado,
um cliente que não lê (portátil suspenso, `Ctrl+S` no terminal) encheria o buffer
de envio, o `send()` bloqueava, e o chat inteiro parava (§2.4 e §3.2 do
`typical-problems.md`).

Mas enviar fora do lock abre uma janela: entre tirar o retrato e enviar, o
cliente pode sair, o `struct` ser libertado e o `fd` fechado. **E o kernel
reutiliza o número do `fd` na ligação seguinte** — a mensagem iria para o cliente
errado, sem crash, sem erro, sem forma de dar por isso.

**A decisão.** `roster_snapshot()` incrementa o `refs` de cada cliente **dentro**
do lock, ao mesmo tempo que lê o ponteiro; quem envia larga a referência no fim.
O `fd` só é fechado quando `refs` chega a zero.

*Alternativas consideradas:* um `rwlock` mantido durante o envio (muito mais
simples, mas um cliente lento bloquearia as saídas — exactamente o problema que
queríamos evitar) e slots fixos com contador de geração (sem alocação, mas com
limite rígido e uma indirecção a mais para explicar).

### D8 — Três destinos em vez de um

`session_handle()` passa a devolver `struct sess_out` (mensagem **+** destino):
`SESS_SELF`, `SESS_ALL`, `SESS_OTHERS`.

A session **continua a não saber que o roster existe** — diz apenas *para quem*,
e é o `main.c` que resolve o *quem*. É isso que a mantém testável sem rede: 58
verificações sem um único socket.

Consequência do D5 (o emissor recebe o próprio `CHAT`): o "eco como CHAT" do M1
**não foi código deitado fora**. Passou de `SELF` a `ALL` e o que o emissor vê é
exactamente o mesmo. O M1 era a especialização a um cliente do comportamento
final.

### D9 — Só se entra no chat depois do `NICK`

Entre o `accept()` e o `NICK` aceite, a ligação existe mas **não faz parte do
chat**: não recebe `CHAT` nem `EVENT`. Daí o `roster_join()` e o campo `joined`.

Foi um bug encontrado pelo `probe_m2.py`, não uma ideia à partida — ver as notas.

### D10 — Texto e destinatários dos `EVENT`

`"<nick> joined"` e `"<nick> left"` (o exemplo do slide 124 é `"rui joined"`),
para **todos menos o próprio**. Quem sai antes de escolher nick não gera `EVENT`
nenhum: ninguém sabia que estava lá.

Está no `PROTOCOL.md` v0.3 como proposta, por acordar com os outros grupos.

## Notas / o que aprendi

> **Saber dizer isto sem ler é o objetivo.**

### 1. Porque é que o `wlock` é por cliente e não global

Um lock global na escrita resolveria a intercalação de mensagens (§3.3) com
muito menos código. E seria um erro: com um lock global, um único cliente que
não lê bloqueia **todas** as escritas do servidor, incluindo as dirigidas a
clientes saudáveis. Por cliente, um cliente lento só atrasa quem lhe escreve.

É a mesma lógica do D7: **o lock protege uma estrutura, nunca a E/S.**

### 2. A ordem dos locks, e porque não há deadlock

Há dois locks: `roster.lock` e, em cada cliente, `wlock`. A regra é **nunca os
segurar ao mesmo tempo** — o `deliver()` larga o primeiro antes de pegar no
segundo. Com dois locks que nunca se aninham, não há ciclo possível, logo não há
deadlock possível. É uma propriedade que se demonstra, não que se testa.

### 3. Porque é que o cliente não precisa de locks e o servidor precisa

Uma ligação TCP é **full-duplex**: os dois sentidos são independentes. No cliente
cada thread usa um sentido só (a principal escreve, a de leitura lê), por isso
nada é partilhado. No servidor há N threads a escrever no **mesmo** socket de um
cliente — daí o `wlock`.

### 4. `volatile` não serve para threads

A flag `quitting` do cliente começou como `volatile sig_atomic_t`. O
ThreadSanitizer apontou uma data race, e tinha razão: esse é o idioma para
**sinais**, e não dá garantia nenhuma de sincronização entre **threads**.
Passou a `_Atomic int` (C11).

Nunca se manifestaria em testes — em x86 um `int` alinhado é atómico na prática —
e nenhuma das outras ferramentas o apanha. Foi o TSan ou nada.

### 5. O que o ASan **não** faz, e o que o TSan **também não**

O AddressSanitizer apanha use-after-free e overflows; **não apanha data races**.
Para isso é o ThreadSanitizer, e são incompatíveis entre si — têm de correr em
compilações separadas.

E o TSan também tem um limite que descobrimos ao tentar validá-lo: tirámos o
`wlock` de propósito e ele **não detetou nada**. A razão é que a corrida aí não é
de memória (o buffer é local de cada thread, o `fd` é só lido) — é **lógica, ao
nível do socket**. Ferramentas de memória não a vêem.

Pior: com `SO_SNDBUF` de 16 KB e linhas de 4 KB, o `send_all()` quase nunca faz
mais de uma iteração, por isso a intercalação **nem chega a acontecer** em
condições normais. O `wlock` é protecção para o buffer cheio — cliente que não lê
—, que é cenário de M4. Fica **justificado mas não demonstrado**, e é mais honesto
dizê-lo do que mostrar um TSan limpo como se cobrisse o caso.

### 6. Um teste mal escrito parece um bug do código

O primeiro teste dos dois clientes falhou em *"a ana é avisada de que o rui
entrou"*. O código estava certo: eu tinha lançado os dois clientes ao mesmo
tempo, e se o `rui` fizer `NICK` primeiro a `ana` ainda não está no chat — logo,
e corretamente, não recebe o aviso. Sequenciar as entradas resolveu.

Lição para os testes de concorrência: **o que não for sequenciado é
indeterminado**, e assumir uma ordem que não foi imposta dá falhas que parecem
bugs.

## Como reproduzir

```sh
make && make test            # 497 verificações
make test SAN=1              # ASan + UBSan

# três clientes reais: broadcast, EVENT, quem NÃO deve receber o quê
python3 scripts/probe_m2.py

# dois clientes a conversar, à mão
./bin/server 5000
./bin/client 127.0.0.1 5000 ana      # noutro terminal
./bin/client 127.0.0.1 5000 rui      # e noutro

# ThreadSanitizer (não combina com o ASan: compilação à parte)
gcc -std=c11 -g -Iinclude -D_POSIX_C_SOURCE=200809L -fsanitize=thread -pthread \
    src/server/*.c src/common/*.c -o /tmp/server_tsan -lcjson
```

O que experimentar à mão, que os testes não cobrem:

- `Ctrl+Z` num cliente (suspende) e escrever nos outros → **ninguém bloqueia**.
  Era o §2.4; com o envio fora do lock deixou de acontecer.
- `kill -9` num cliente → o servidor regista o RST e os outros continuam.
- Matar o servidor com clientes ligados → cada um avisa e sai com 0.
