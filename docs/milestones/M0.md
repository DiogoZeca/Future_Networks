## O que foi implementado

| Ficheiro | Conteúdo |
|---|---|
| `include/net.h`, `src/common/net.c` | Funções de sockets reutilizadas nas fases seguintes |
| `src/server/main.c` | Servidor de eco iterativo (um cliente de cada vez) |
| `src/client/main.c` | Cliente: lê do teclado, envia, espera pelo eco completo |
| `scripts/probe_m0.py` | Sonda com cenários difíceis de reproduzir à mão (ver `scripts/README.md`) |

Decisões e porquês:

- **`getaddrinfo()`** em vez de preencher `sockaddr_in` à mão (recomendado nos
  slides). O cliente aceita nome ou IP e tenta cada endereço devolvido:
  `localhost` resolve primeiro para `::1` (IPv6), que falha, e depois para
  `127.0.0.1`.
- **Servidor em `0.0.0.0`** (todas as interfaces), para aceitar ligações de
  outras máquinas e não só de `localhost`. Só IPv4.
- **`SO_REUSEADDR`** para reiniciar o servidor sem `Address already in use`.
- **`send_all()`**: `send()` pode aceitar só parte do buffer; repete até
  enviar tudo.
- **`MSG_NOSIGNAL`**: enviar para uma ligação já fechada gera `SIGPIPE`, que
  mata o processo sem mensagem nenhuma. Com a flag, `send()` devolve erro.
- **`recv_retry()`**: repete o `recv()` se for interrompido por um sinal (`EINTR`).
- **O cliente lê o eco em ciclo até ter os `len` bytes enviados**, porque um
  `recv()` pode devolver menos do que foi enviado.
- **Ctrl+D no cliente faz `shutdown(SHUT_WR)`** (half-close, slide 87): fecha
  só o sentido de envio e continua a ler até o servidor fechar.
- **`setvbuf(stdout, ..., _IOLBF)` no servidor**: os logs aparecem logo,
  mesmo com o output redirecionado para um ficheiro ou pipe.

## Testes passo a passo (Ubuntu)

### 0. Preparação

```sh
sudo apt install build-essential netcat-openbsd wireshark
sudo usermod -aG wireshark $USER    # capturar sem sudo; requer logout/login
make clean && make                  # gera bin/server e bin/client
```

Verificar: `gcc --version`, `make --version`, `nc -h` (deve dizer *OpenBSD
netcat*), `ss -V`, `groups | grep wireshark`.

São precisos até 4 terminais, todos na raiz do repositório.

### 1. Eco básico

```sh
./bin/server              # terminal 1 (porta 5000 por omissão)
./bin/client localhost    # terminal 2
```

Escrever algumas linhas e terminar com **Ctrl+D**.

**Esperado:**
- No cliente: `[eco em 1 recv] <texto>`.
- No servidor: `ligado: 127.0.0.1:<porta>`, um `recv de N bytes` por linha e,
  no fim, `desligado: ... (T bytes ecoados)`.
- O servidor continua à espera do próximo cliente.

**Porquê:**
- N = número de caracteres + 1, porque o `\n` do Enter também é enviado.
  Exemplo: `ola` dá 4 bytes. Com 9 linhas, o total foi 43 bytes.
- A porta do cliente é escolhida pelo kernel, porque o cliente nunca faz
  `bind()`.

### 2. Ver as ligações no sistema (`ss`)

Com o servidor a correr e um cliente ligado, no terminal 3:

```sh
ss -tnp state all '( sport = :5000 or dport = :5000 )'
```

**Esperado:**

```
State   Recv-Q Send-Q  Local Address:Port  Peer Address:Port  Process
LISTEN  0      8       0.0.0.0:5000        0.0.0.0:*          server, fd=3
ESTAB   0      0       127.0.0.1:35748     127.0.0.1:5000     client, fd=3
ESTAB   0      0       127.0.0.1:5000      127.0.0.1:35748    server, fd=4
```

Depois de fechar o cliente (Ctrl+D) e repetir o comando, fica o `LISTEN` e
aparece `TIME-WAIT` em `127.0.0.1:35748 → 127.0.0.1:5000`.

**Porquê:**
- O servidor tem **dois sockets**:
  - o de escuta (`fd=3`), criado por `tcp_listen()`;
  - um novo por cliente (`fd=4`), devolvido por `accept()`.
  Os fd 0, 1 e 2 são stdin, stdout e stderr.
- Cada ligação é identificada pelo 4-tuple (IP origem, porta origem, IP
  destino, porta destino) e aparece duas vezes, uma de cada lado.
- Num socket `LISTEN`:
  - `Send-Q` é o tamanho máximo da fila de ligações por aceitar: o `8` de
    `tcp_listen(port, 8)`;
  - `Recv-Q` é quantas ligações estão nessa fila agora.
- `TIME-WAIT` fica do lado de **quem fechou primeiro** (aqui, o cliente),
  durante cerca de 60 s. Não tem processo associado, porque pertence só ao kernel.

### 3. O `nc` como cliente

```sh
nc localhost 5000
```

**Esperado:** o eco aparece tal e qual, sem prefixo, e os logs do servidor são
iguais aos do passo 1.

**Porquê:** o servidor só vê bytes a chegar por TCP e não sabe que programa
está do outro lado. É a base da interoperabilidade: o `nc` serve para testar
servidores de outros grupos sem o cliente deles. Uma linha vazia chega como
`recv de 1 bytes` (só o `\n`).

> Com `printf 'ola\n' | nc localhost 5000` (sem `-N`), o `nc` não faz
> half-close ao ver EOF e fica parado até Ctrl+C. Ver nota 6.

### 4. O servidor só atende um cliente de cada vez

1. Terminal 2: `./bin/client localhost`, escrever `primeiro`. Recebe eco.
   **Deixar aberto.**
2. Terminal 3: `./bin/client localhost`, escrever `segundo`. **Não recebe eco.**
3. Terminal 4: correr o `ss` do passo 2.
4. Fechar o cliente A (Ctrl+D).

**Esperado no `ss`:**

```
LISTEN  1  8   0.0.0.0:5000      0.0.0.0:*          server
ESTAB   0  0   127.0.0.1:42870   127.0.0.1:5000     client (B)
ESTAB   0  0   127.0.0.1:54692   127.0.0.1:5000     client (A)
ESTAB   8  0   127.0.0.1:5000    127.0.0.1:42870    (sem processo)
ESTAB   0  0   127.0.0.1:5000    127.0.0.1:54692    server, fd=4
```

Ao fechar A, o B recebe logo o eco e o servidor mostra, de seguida,
`desligado` (A), `ligado` (B) e `recv de 8 bytes`. O B passa a ter `fd=4`.

**Porquê:**
- O ciclo do servidor é `accept()` → `recv/send` até `recv()==0` →
  `close()` → `accept()`. Enquanto A está ligado, o programa está bloqueado
  no `recv()` de A e não volta ao `accept()`. É o esperado no M0: o slide 86
  diz *"This version serves one client at a time"*.
- O **kernel** faz o handshake de B e guarda a ligação na fila do `listen`
  (`Recv-Q 1` no `LISTEN`). Ver nota 1.
- Os bytes de `segundo\n` já estão no buffer do kernel (`Recv-Q 8`) à espera
  de um `recv()`. Não se perdem.
- A linha do B do lado do servidor não tem processo porque ainda ninguém fez
  `accept()` dela.
- O B herda o `fd=4` porque o `close()` de A o libertou, e o kernel atribui
  sempre o número livre mais baixo.

### 5. Os limites das mensagens

**5a. Várias linhas num só `recv`:**

```sh
printf 'a\nb\nc\n' | nc -N localhost 5000
```

**Esperado:** no servidor, **um único** `recv de 6 bytes`.

**5b. Uma mensagem em vários `recv`:**

```sh
python3 -c "print('x'*100000)" | nc -N localhost 5000 | wc -c
```

**Esperado:** 24 × `recv de 4096 bytes` + `recv de 1697 bytes` (= 100001); o
`wc -c` mostra `100001`.

**Porquê:**
- O TCP é um fluxo de bytes e não preserva as fronteiras dos `send()`.
  Três "mensagens" chegam juntas (5a) e uma chega partida (5b).
- O tamanho de cada `recv` depende do nosso buffer (4096) e do momento em que
  lemos, não da forma como o outro lado enviou. Em 5b os dados acumularam-se
  no kernel e cada `recv` encheu o buffer todo. Ver nota 2.

### 6. Fechos bruscos

**6a. O cliente morre:** ligar um cliente e carregar **Ctrl+C** nele.

- **Esperado:** o servidor mostra `desligado` na mesma.
- **Porquê:** quando um processo termina, o kernel fecha os seus sockets e
  envia FIN, por isso o `recv()` do servidor devolve 0.

**6b. O servidor morre:**
1. Ligar um cliente.
2. Ctrl+C no servidor.
3. Correr o `ss`.
4. No cliente, escrever algo.

**Esperado no `ss`:**

```
FIN-WAIT-2  0  0  127.0.0.1:5000    127.0.0.1:48498   (sem processo)
CLOSE-WAIT  1  0  127.0.0.1:48498   127.0.0.1:5000    client
```

Ao escrever no cliente, aparece `[client] o servidor fechou a ligação`.

**Porquê:**
- O kernel do servidor enviou FIN em nome do processo morto e ficou em
  `FIN-WAIT-2` à espera do FIN do cliente.
- O cliente recebeu o FIN (é o `1` no `Recv-Q`), mas está bloqueado no
  `fgets` à espera do teclado, por isso **não dá por nada** (`CLOSE-WAIT`).
- Ao escrever:
  - o `send()` funciona, porque o kernel aceita os dados;
  - o socket do servidor já não tem dono e responde com **RST**, que destrói
    a ligação (por isso não fica `TIME-WAIT`);
  - o `recv()` do cliente devolve 0, porque o FIN já estava na fila.

**6c. Reiniciar o servidor (`SO_REUSEADDR`):**
1. Ligar um cliente.
2. Ctrl+C no servidor.
3. Sair do cliente com **Ctrl+D**, que é um fecho limpo, sem RST.
4. O `ss` mostra `TIME-WAIT` do lado `127.0.0.1:5000`.
5. Correr `./bin/server` de imediato.

- **Esperado:** o servidor arranca sem erro.
- **Porquê:** quem fechou primeiro foi o servidor, por isso o `TIME-WAIT`
  fica na porta 5000. Sem `SO_REUSEADDR`, o `bind()` recusa essa porta. Ver
  nota 5.
- **Verificado:** o mesmo cenário com um binário compilado sem a linha
  `setsockopt(...)` dá `bind/listen: Address already in use`.

> Atenção: se em vez de Ctrl+D se escrever algo no cliente (como em 6b), a
> ligação acaba com RST, não fica `TIME-WAIT`, e o teste não prova nada.

## Análise da captura (`docs/captures/m0-handshake.pcap`)

10 pacotes. Notação do `tcpdump`: `[S]` SYN, `[S.]` SYN+ACK, `[.]` ACK puro,
`[P.]` PSH+ACK (dados), `[F.]` FIN+ACK, `[R]` RST.

| # | delta t | Direção | Flags | O que é |
|---|---|---|---|---|
| 1 | - | cli → srv | `[S]` | SYN. `seq=198145416`, anuncia `mss 65495`, `wscale 10`, `sackOK` |
| 2 | +12 µs | srv → cli | `[S.]` | SYN+ACK. `ack=198145417` (= seq+1) |
| 3 | +9 µs | cli → srv | `[.]` | ACK. **Ligação estabelecida: 21 µs no total** |
| 4 | +4,48 s | cli → srv | `[P.]` | `length 4`: o `ola\n` |
| 5 | +10 µs | srv → cli | `[.]` | ACK do **kernel** |
| 6 | +73 µs | srv → cli | `[P.]` | `length 4`: o eco, da **aplicação** |
| 7 | +6 µs | cli → srv | `[.]` | ACK ao eco |
| 8 | +9,60 s | cli → srv | `[F.]` | FIN: o Ctrl+D → `shutdown(SHUT_WR)` |
| 9 | +70 µs | srv → cli | `[F.]` | FIN do servidor: viu `recv()==0` e fechou |
| 10 | +10 µs | cli → srv | `[.]` | Fecho completo |

Os dois intervalos longos (4,48 s e 9,60 s) são a pessoa a escrever. Entre
eles, **zero pacotes**: uma ligação TCP aberta e parada não gasta nada. Por isso
o servidor não consegue distinguir "utilizador calado" de "máquina desligada".

### O que esta captura prova

1. **O `accept()` não aparece no fio.** Os pacotes 1–3 são feitos inteiramente
   pelo kernel.
2. **O ACK do TCP não é a resposta da aplicação.** No par #5/#6, o kernel
   acusou a receção em 10 µs e a aplicação só respondeu 73 µs depois. Se o
   servidor tivesse crashado entre os dois, o cliente recebia o ACK e nunca o
   eco. **Receber ACK não prova que a aplicação processou a mensagem.**
3. **O fecho foi em 3 pacotes, não nos 4 do manual.** O servidor juntou o ACK
   ao seu próprio FIN (#9), porque ao ver `recv()==0` não tinha mais nada para
   enviar e fechou logo.
4. **O FIN consome um número de sequência.** O FIN vai com `seq 5` e
   `length 0`, mas a resposta é `ack 6`.
5. **`win 65495` no SYN e `win 64` depois não é um bug.** Foi negociado
   `wscale 10`, logo a janela real é `64 << 10` = 65 536 bytes. O `tcpdump`
   mostra o campo em bruto depois do handshake.
6. **O `length 4` confirma que o `\n` vai no fio:** são os 4 bytes de `ola\n`.

**Numa segunda captura (Wireshark, com `ola` e `mundo`)**, o ACK ao `ola` foi
sozinho (como #5), mas o ACK ao `mundo` foi à boleia do próprio eco. É o kernel
que decide, não o nosso código. Nessa captura vê-se também que a sequência
conta bytes, não mensagens: no fim, Seq=11 = 4 + 6 bytes de dados + 1 do SYN.

## Notas / o que aprendi

> Saber dizer isto sem ler é o objetivo: são as perguntas prováveis na defesa.

### 1. Quando acontece o handshake em relação ao `accept()`?

O handshake é feito **inteiramente pelo kernel**, a partir do momento em que o
socket está em `listen()`:
1. Chega um SYN e o kernel responde SYN-ACK.
2. Ao receber o ACK final, o kernel coloca a ligação, **já estabelecida**, numa
   fila: a *backlog* do `listen(fd, 8)`.

O `accept()` não participa no handshake. Limita-se a **retirar uma ligação da
fila** e a devolver um descritor novo, dedicado a esse cliente.

Por isso, no passo 4 e no probe, o 2.º cliente estava ligado ao nível do TCP
mas nunca foi servido. **Ligado ao nível do TCP não é o mesmo que aceite pela
aplicação.**

### 2. Porque é que 10 001 bytes chegaram em 3 `recv()`? De onde vem o 4096?

Porque **o TCP é um byte stream**: garante que os bytes chegam todos e pela
mesma ordem, mas **não preserva as fronteiras dos `send()`**.

O 4096 é o nosso `BUF_SIZE`, o tamanho que passamos ao `recv()`. O `recv()`
devolve no máximo o que lhe pedimos e devolve o que estiver disponível naquele
instante. Daí 4096 + 4096 + 1809 = 10 001. Com `BUF_SIZE` de 1024 seriam 10
leituras. O que vem do TCP é **não haver alinhamento entre `send()` e `recv()`**.

### 3. Diferença entre `recv()==0` e `recv()==-1` com `ECONNRESET`

| | `recv() == 0` | `recv() == -1`, `errno == ECONNRESET` |
|---|---|---|
| O que chegou | **FIN** | **RST** |
| Significa | fecho ordeiro: o peer não vai enviar mais nada (pode ainda estar a receber) | fecho abrupto: peer morto, `kill -9`, ou fechou com dados por ler |
| É erro? | **Não**: é fim de stream e `errno` não é alterado | Sim |
| O que sabemos | só que o peer acabou de enviar; **não** prova que leu o que lhe enviámos | nada; dados em trânsito podem ter-se perdido |

Ambos têm de ser tratados. Testar só `n <= 0` junta os dois casos: funciona,
mas perde-se a distinção no log. **Não testar o `0` faz o servidor entrar em
ciclo infinito a 100% de CPU** sobre um socket morto (slide 125).

### 4. Porque é que um `close()` normal pode gerar RST em vez de FIN?

FIN significa "enviei tudo o que tinha". Se a aplicação faz `close()` com
**dados recebidos por ler**, esses dados vão ser deitados fora, e o kernel
sinaliza isso enviando **RST** em vez de FIN.

No probe, o 2.º cliente fecha logo a seguir ao 1.º. Se o eco do servidor chega
antes desse `close()`, o cliente tem dados por ler e sai RST. Se chega depois,
sai FIN. Por isso o resultado depende do timing.

**Consequência:** um cliente bem comportado pode aparecer ao servidor como uma
ligação abortada. O servidor não pode assumir que um `close()` do outro lado
produz sempre `recv()==0`.

### 5. O que resolve o `SO_REUSEADDR`? Que estado do TCP está envolvido?

**`TIME_WAIT`.** Quem fecha ativamente a ligação fica nesse estado durante
2×MSL (60 s no Linux), para:
- apanhar pacotes atrasados da ligação antiga;
- garantir que o último ACK chega ao outro lado.

Durante esse tempo, um `bind()` novo na mesma porta falha com `EADDRINUSE`.
Isto só acontece quando foi **o servidor** a fechar primeiro (passo 6c).

`SO_REUSEADDR` autoriza o `bind()` mesmo havendo ligações em `TIME_WAIT` nessa
porta. **Não** permite dois servidores à escuta na mesma porta em simultâneo;
isso seria `SO_REUSEPORT`.

### 6. Porque é que o `nc` precisou de Ctrl+C?

```sh
printf 'ola\n' | nc 127.0.0.1 5000     # ecoou "ola" e ficou parado
```

O `printf` termina e fecha o stdin do `nc`, mas o `openbsd-netcat` **não** faz
`shutdown(SHUT_WR)` ao ver EOF: fica à espera de mais dados do servidor. Com
`nc -N` faz o half-close e sai sozinho.

Durante esse tempo, o nosso servidor (iterativo) ficou **preso nesse cliente**
e qualquer outro ficaria em fila: **um cliente que não fecha bloqueia toda a
gente** (ver §2.4 de [`docs/typical-problems.md`](../typical-problems.md)).

Lição de interoperabilidade: **nem todos os clientes fecham da mesma maneira.**
O nosso cliente faz half-close, o `nc` não faz nada e o probe manda RST. O
servidor tem de aguentar os três.

### 7. Estados TCP observados com o `ss`

| Estado | Significado | Onde se viu |
|---|---|---|
| `LISTEN` | Socket à espera de ligações | passo 2 |
| `ESTAB` | Ligação aberta | passos 2 e 4 |
| `FIN-WAIT-2` | Já enviámos FIN e recebemos ACK; à espera do FIN do outro lado | passo 6b (servidor) |
| `CLOSE-WAIT` | Recebemos FIN, mas a aplicação ainda não fechou | passo 6b (cliente) |
| `TIME-WAIT` | Fecho concluído; o lado que fechou primeiro espera cerca de 60 s | passos 2 e 6c |

O cliente parado em `CLOSE-WAIT` (passo 6b) mostra que **o cliente atual não
consegue reagir ao servidor enquanto espera pelo teclado**.
