# M1 — Framing e protocolo

> *"Newline-delimited JSON messages; a recv buffer that handles partial and merged
> messages; NICK and MSG."* — slide 123

**Objetivo:** deixar de tratar bytes e passar a tratar **mensagens**.

## Porque é que este milestone existe

No M0 medimos: um `send()` de 10 001 bytes chegou em **três `recv()`** (4096 + 4096
+ 1809). Com JSON, o primeiro pedaço é texto inválido. O inverso também acontece:
duas mensagens rápidas chegam num só `recv()`.

O M1 é a camada que converte *stream de bytes* em *sequência de mensagens*. É a
peça com mais bugs subtis de todo o projeto, e é a que o M2 e o M3 assumem como
resolvida.

## O que os slides pedem (slides 123–125)

| Slide | Diz | Para nós significa |
|---|---|---|
| 123 | *"Newline-delimited JSON messages"* | 1 mensagem = 1 objeto JSON numa linha terminada em `\n` |
| 123 | *"a recv buffer that handles partial and merged messages"* | buffer **persistente por ligação** (`struct rxbuf`) — partidas e coladas |
| 123 | *"NICK and MSG"* | só estes dois tipos C→S; do lado S→C bastam `OK`, `CHAT`, `ERROR` |
| 124 | tabela de mensagens | nomes e campos **fixos** — `NICK` tem de ser a primeira mensagem |
| 125 | *"Two send() calls can arrive in one recv(), or one send() can require many recv() calls"* | testes de framing #2, #3, #4 |
| 125 | *"fixed-size records, a delimiter with escaping, or a length prefix"* | usamos **delimitador**; o *escaping* é feito pelo próprio JSON (um `\n` dentro de `text` é serializado como `\\n`, logo nunca há `0x0A` literal dentro de uma mensagem). O *length prefix* volta no M6-A (ficheiros binários) |
| 125 | *"Start early!!! Interop from the first moment!"* | checkpoint de interop no fim do M1 (ver abaixo) |

Só o código `409` vem dos slides; `400` e `401` são propostas nossas (`PROTOCOL.md` §5).

## O que muda em relação ao M0

| | M0 — eco | M1 — framing + protocolo |
|---|---|---|
| Unidade de trabalho | **bytes**: cada `recv()` tratado tal como veio | **mensagens**: só linhas completas |
| Estado por ligação | nenhum | `struct rxbuf` (sobrevive entre `recv()`) + estado `AWAITING_NICK`/`READY` |
| O servidor responde | os mesmos bytes | `OK` / `CHAT` / `ERROR` em JSON |
| Erros a tratar | só de socket (`recv()==0`, `ECONNRESET`) | também **do peer**: JSON inválido, campo em falta/tipo errado, linha longa, `MSG` antes de `NICK` |
| Cliente | envia a linha e lê exatamente `len` bytes de eco | envia `NICK` ao ligar e `MSG` por linha; lê **linhas** (também com `rxbuf`) — a resposta já não tem o tamanho do que se enviou |
| Dependências | só libc | + cJSON (`-lcjson`) |
| Testes | manuais: `nc`, `probe_m0.py`, Wireshark | + unitários sem rede: `make test` / `make test SAN=1` |
| **Mantém-se** | `net.c` (`tcp_listen`, `send_all`, `recv_retry`); servidor **iterativo** | igual — 1 cliente de cada vez (concorrência é M2) |

## Arquitetura

Duas camadas novas, ambas **sem rede** — é o que as torna testáveis à unidade:

```
  socket  ──bytes──▶  framing  ──linhas──▶  protocol  ──struct msg──▶  lógica
                     (rxbuf)              (cJSON)
```

| Ficheiro | Responsabilidade | Não faz |
|---|---|---|
| `include/framing.h` + `src/common/framing.c` | bytes ↔ linhas | não sabe o que é JSON |
| `include/protocol.h` + `src/common/protocol.c` | linhas ↔ `struct msg` validada | não toca em sockets |

Esta separação não é estética: permite testar o pior caso (mensagens partidas) com
testes puros, sem rede, de forma determinística. Com rede, metade destes casos é
impossível de reproduzir à vontade.

### Camada 1 — `framing`

Estado por ligação: um `struct rxbuf` por cliente, vive enquanto a ligação viver.
O contrato final (4 campos, 4 valores de retorno, `out_len`) está em
`include/framing.h`; o **porquê** de cada decisão está em [`docs/framing.md`](../framing.md).

Ciclo de uso no servidor:

```
n = recv(...)                                 /* 1 recv */
if (n <= 0) -> tratar fecho
if (rxbuf_feed(&rx, buf, n) != 0) -> fechar
for (;;) {                                    /* 0..N mensagens */
    r = rxbuf_next_line(&rx, line, sizeof line, &len);
    if (r == RX_NEED) break;                  /* faltam bytes: voltar ao recv() */
    if (r != RX_LINE) -> fechar               /* RX_TOOLONG / RX_FAULT */
    processar(line, len);
}
```

Ramificar em **três**: com `while (... == 1)` o erro (`-1`) fica indistinguível de
"faltam bytes" (`0`) e volta-se ao `recv()` com o buffer envenenado.

O `while` é o ponto essencial: **um `recv()` pode produzir zero, uma, ou muitas
mensagens.** Um `if` em vez de um `while` é o bug clássico — funciona em todos os
testes manuais e falha quando duas pessoas escrevem ao mesmo tempo.

Detalhes que a implementação tem de respeitar:
- procurar `\n` (0x0A) só nos bytes ainda não examinados;
- se a linha terminar em `\r`, descartá-lo (`\r\n` está aceite na spec);
- `memmove` do resto para o início depois de extrair — simples e suficiente para
  linhas de 4 KB; um ring buffer aqui é otimização prematura;
- linha vazia → ignorar, não é erro (tolerância a emissores com bugs);
- **nunca** escrever para lá de `RX_CAP`.

### Camada 2 — `protocol`

Converte uma linha numa estrutura validada e vice-versa. Só os tipos do M1 —
`NICK`, `MSG`, `OK`, `ERROR`, `CHAT` — os restantes entram no M3. Contrato em
`include/protocol.h`; decisões e limites em [`docs/protocol-layer.md`](../protocol-layer.md).

Regras de validação, por cada campo lido:
1. o item existe (`cJSON_GetObjectItemCaseSensitive` != `NULL`);
2. é do tipo certo (`cJSON_IsString`, `cJSON_IsNumber`);
3. o comprimento está dentro do limite.

Falhar qualquer uma → `ERROR 400`. **Nunca** `item->valuestring` sem verificar
antes — é `NULL` para campos ausentes e dá segfault imediato.

Gestão de memória (fonte garantida de fugas):
- cada `cJSON_Parse()` precisa de `cJSON_Delete()`, **incluindo nos caminhos de erro**;
- `cJSON_PrintUnformatted()` devolve memória que tem de ser libertada;
- usar `cJSON_PrintUnformatted()`, **nunca** `cJSON_Print()` — este último mete
  newlines e parte o enquadramento.

### Máquina de estados do servidor (por ligação)

```
   [novo socket]
         │
         ▼
  AWAITING_NICK ──NICK válido──▶ READY ──MSG──▶ eco/broadcast
         │                         │
         │ outro tipo              │ JSON inválido
         ▼                         ▼
     ERROR 401                 ERROR 400
```

No M1 ainda não há lista de clientes, por isso o `MSG` pode simplesmente devolver
um `CHAT` ao próprio emissor. O broadcast a sério é M2. O que interessa aqui é que
a **máquina de estados** e o **enquadramento** fiquem certos.

## Decisões a tomar no M1

Nenhuma delas é óbvia, e todas aparecem na interoperabilidade. Decidir **antes** de
escrever código e registar no `PROTOCOL.md`.

### D1 — Capacidade do buffer vs. linha máxima ❗
A spec propõe linha máxima de 4096 bytes incl. `\n`. O `BUF_SIZE` dos `main.c`
também é 4096. **Estes dois números não podem ser iguais**: o buffer tem de poder
conter o resto da leitura anterior *mais* uma linha completa.

*Recomendação:* `RX_CAP = 8192`, linha máxima 4096. Ao exceder: `ERROR 400` e
fechar a ligação. Não truncar em silêncio — os bytes a seguir seriam lidos como
uma mensagem nova e tudo descarrilava a partir daí.

### D2 — O que fazer a uma linha demasiado longa
*Recomendação:* `ERROR 400` + fechar. Tentar ressincronizar (descartar até ao
próximo `\n`) parece simpático mas é pior: não se sabe se esse `\n` é o fim da
linha gigante ou o meio de outra coisa.

### D3 — UTF-8
*Recomendação:* **não descodificar**. Tratar como bytes opacos até haver linha
completa. Partir em `\n` é sempre seguro em UTF-8 — todos os bytes de continuação
são ≥ 0x80, por isso 0x0A nunca ocorre dentro de um caracter multibyte. Validar
UTF-8 é trabalho do M4, se for preciso de todo.

### D4 — Limites de `nick` e `text`
Está *TO AGREE* na spec. Propor aos outros grupos: `nick` ≤ 32 bytes, `text` ≤ 1024
bytes, ambos sem `\n`. Sem acordo, um grupo aceita o que outro rejeita.

### D5 — O emissor de `MSG` recebe o próprio `CHAT`?
Já está em aberto no `PROTOCOL.md` §4. **Decidir agora**, porque muda o que o
cliente mostra no ecrã: se não receber, tem de imprimir localmente o que escreveu;
se receber, imprimir localmente **duplica** a mensagem. Com dois grupos a decidir
ao contrário, parece um bug de rede e perde-se uma tarde a procurá-lo.
*Recomendação:* o emissor **recebe** o seu `CHAT` — é mais simples no servidor, e
dá ao utilizador confirmação de que a mensagem chegou mesmo ao servidor.

### D6 — Há `OK` ao `NICK`?
*Recomendação:* sim. Dá ao cliente um ponto claro para passar ao estado "ligado" e
é a única forma de distinguir "nick aceite" de "servidor ainda a pensar".

## Checkpoint de interoperabilidade

A partir do M1 já dá para testar contra outros grupos, e o slide 125 insiste nisso
(*"Start early!!!"*). Não é preciso o cliente deles:

```sh
printf '{"type":"NICK","nick":"ana"}\n{"type":"MSG","text":"ola"}\n' | nc <host> 5000
```

Dois testes a fazer com outro grupo **antes** de avançar para o M2:
1. o nosso servidor aceita a sequência acima enviada por eles;
2. o nosso cliente aguenta as respostas do servidor deles.

Qualquer divergência aqui é uma secção *TO AGREE* por fechar — resolver na spec,
não no código.
