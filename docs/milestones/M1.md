## O que os slides pedem (slides 123–125)

| Slide | Diz | Para nós significa |
|---|---|---|
| 123 | *"Newline-delimited JSON messages"* | 1 mensagem = 1 objeto JSON numa linha terminada em `\n` |
| 123 | *"a recv buffer that handles partial and merged messages"* | buffer **persistente por ligação** (`struct rxbuf`) — partidas e coladas |
| 123 | *"NICK and MSG"* | só estes dois tipos C→S; do lado S→C bastam `OK`, `CHAT`, `ERROR` |
| 124 | tabela de mensagens | nomes e campos **fixos** — `NICK` tem de ser a primeira mensagem |
| 125 | *"Two send() calls can arrive in one recv(), or one send() can require many recv() calls"* | é exatamente o que os testes e o `interop.py` provocam |
| 125 | *"fixed-size records, a delimiter with escaping, or a length prefix"* | usamos **delimitador**; o *escaping* é feito pelo próprio JSON (um `\n` dentro de `text` é serializado como `\\n`, logo nunca há `0x0A` literal dentro de uma mensagem). O *length prefix* volta no M6-A (ficheiros binários) |
| 125 | *"Start early!!! Interop from the first moment!"* | `scripts/interop.py` e `tests/interop/` prontos para usar com outro grupo |

## O que muda em relação ao M0

| | M0 — eco | M1 — framing + protocolo |
|---|---|---|
| Unidade de trabalho | **bytes**: cada `recv()` tratado tal como veio | **mensagens**: só linhas completas |
| Estado por ligação | nenhum | `struct rxbuf` (sobrevive entre `recv()`) + `struct session` (`AWAITING_NICK`/`READY`) |
| O servidor responde | os mesmos bytes | `OK` / `CHAT` / `ERROR` em JSON |
| Erros a tratar | só de socket (`recv()==0`, `ECONNRESET`) | também **do peer**: JSON inválido, campo em falta/tipo errado, linha longa, `MSG` antes de `NICK` |
| Cliente | envia a linha e lê exatamente `len` bytes de eco | envia `NICK` ao ligar e `MSG` por linha; lê **linhas** (também com `rxbuf`) |
| Dependências | só libc | + cJSON (`-lcjson`) |
| Testes | manuais: `nc`, `probe_m0.py`, Wireshark | + 4 suites unitárias sem rede, `interop.py`, `probe_client.py` |
| **Mantém-se** | `net.c` (`tcp_listen`, `send_all`, `recv_retry`); servidor **iterativo** | igual — 1 cliente de cada vez (concorrência é M2) |

## Problemas do M0 resolvidos no M1

No M0 não inventámos problemas: **medimo-los** (`docs/milestones/M0.md`,
`scripts/probe_m0.py`, captura em `docs/captures/`). Enquanto o servidor era um
eco, nenhum deles fazia estragos — bytes para trás são bytes para trás. A partir
do momento em que os bytes têm de ser **interpretados** como mensagens JSON,
todos passam a ser fatais. O M1 existe para os resolver.

### P1 — Uma mensagem chega partida em vários `recv()`

**No M0:** o `probe_m0.py` fez um único `send()` de 10 001 bytes e o servidor
recebeu-o em **três `recv()`: 4096 + 4096 + 1809**. TCP garante ordem e
integridade, **não fronteiras**. No eco era indiferente.

**Porque passou a ser fatal:** com JSON, o primeiro pedaço é texto inválido:

```
recv #1 -> {"type":"MSG","te        <- JSON invalido
recv #2 -> xt":"ola"}               <- JSON invalido
```

Nenhum byte se perdeu na rede, mas se cada `recv()` for tratado como uma
mensagem, as duas metades vão para o lixo.

**Como resolvemos:** nunca se interpreta o que o `recv()` devolveu. Os bytes vão
para um **buffer por ligação** (`struct rxbuf`, `rxbuf_feed()`), e só se extrai o
que já terminar em `\n` (`rxbuf_next_line()`). O que sobra fica guardado para o
próximo `recv()`. O campo `scanned` evita voltar a procurar `\n` nos bytes já
vistos — sem ele, receber byte a byte custaria O(n²).

**Prova:** teste #2 (a mesma mensagem entregue byte a byte: só o último byte
produz uma linha), #4 (mensagem e meia: o resto fica no buffer), #24 (duas
mensagens byte a byte, sem reiniciar); `interop.py` em modo `byte-a-byte`, com
sockets reais e `TCP_NODELAY`.

### P2 — Várias mensagens chegam coladas num `recv()`

**No M0:** o slide 125 avisa (*"Two send() calls can arrive in one recv()"*), mas
num eco não havia como reparar: várias linhas que chegassem coladas eram
devolvidas coladas, tal como vieram. (No M1 vê-se logo: o `printf` com quatro
linhas para o `nc` chegou ao servidor num só `recv()`.)

**Porque passou a ser fatal:** é o pior dos dois casos, porque **falha sem
avisar**:

```
recv #1 -> {"type":"NICK","nick":"ana"}\n{"type":"MSG","text":"ola"}\n
```

O `cJSON_Parse()` lê o primeiro objeto, fica satisfeito e ignora o resto. A `ana`
entra, o "ola" nunca existiu, e não há erro nenhum.

**Como resolvemos**, em três sítios:

1. **Servidor e cliente usam um ciclo, não um `if`**, para tirar linhas do buffer
   depois de cada `recv()` — um `recv()` pode trazer zero, uma ou muitas
   mensagens. E o ciclo tem **três saídas** (`RX_LINE`, `RX_NEED`, erro), não duas:
   com `while (r == 1)` um erro confunde-se com "faltam bytes".
2. **O cliente vê o buffer antes de ir ao `recv()`** (`read_line()`): se duas
   respostas chegaram coladas, a segunda já lá está. Testado como mutação: com a
   ordem trocada, um `CHAT` colado atrás de outra mensagem **desaparecia em
   silêncio** quando o servidor fechava a seguir.
3. **O protocolo recusa lixo depois do objeto** (`cJSON_ParseWithLengthOpts` +
   verificar que só sobram espaços): `{…}{…}` numa só linha é `ERROR 400`, não
   "aceitar o primeiro e esquecer o segundo".

**Prova:** #3 (duas mensagens num feed), #25 (`{…}{…}` → 400); `interop.py` em
modo `colado`; `probe_client.py` cenário `colado_com_event`.

### P3 — O buffer era do mesmo tamanho que a linha máxima

**No M0:** os dois `main.c` tinham `BUF_SIZE 4096`, e a spec propunha linha
máxima de 4096. Registado como armadilha em `typical-problems.md` §1.4 e como
decisão D1.

**Porque é um problema:** depois de tirar as linhas completas sobra um pedaço de
linha (até 4095 bytes); o `recv()` seguinte junta até 4096. Num buffer de 4096,
ou se escreve fora dele (overflow) ou se trunca — e truncar em silêncio faz os
bytes seguintes serem lidos como uma mensagem nova.

**Como resolvemos:**

- `RX_CAP = RX_MAX_LINE + RX_CHUNK = 8192`. Pior caso real: 4095 + 4096 = 8191.
  Um `_Static_assert` garante a relação — se alguém mexer num dos números sem
  pensar, **não compila**. As três constantes vivem no mesmo header.
- Linha com mais de 4096 bytes → o buffer fica **envenenado** (`failed`), o
  servidor responde `ERROR 400 "line too long"` e fecha. **Nunca ressincroniza**
  (D2): depois de uma linha gigante não se sabe onde começa a mensagem seguinte.
- O `recv()` nunca pede mais do que `RX_CHUNK`. Com esta disciplina, o buffer
  **não pode** transbordar.

**Prova:** #6 (5000 bytes sem `\n` → erro, sem overflow — confirmado pelo ASan),
#7 e #21 (4095+`\n` aceite, 4096+`\n` recusado), #22 (executa o pior caso
4095 + 4096), #23 (4096 sem `\n` recusado logo); caso hostil A (ver abaixo).

### P4 — O cliente lia exatamente `len` bytes de eco

**No M0:** o cliente enviava a linha e ficava em `recv()` até ter recebido de volta
**o mesmo número de bytes** que enviou. Só funcionava porque o servidor era um eco.

**Porque deixou de servir:** a resposta a `{"type":"MSG","text":"ola"}` é um
`CHAT` com outro tamanho; a um `NICK` é um `OK` de 14 bytes. Contar bytes deixou de
fazer sentido — o cliente tem exatamente o mesmo problema de enquadramento que o
servidor.

**Como resolvemos:** o cliente tem o seu próprio `rxbuf` e lê **linhas**, como o
servidor (P1, P2). Funciona em pedido-resposta (uma resposta por pedido), com
**timeout de 5 s** (`SO_RCVTIMEO`) para não ficar preso se o servidor de outro grupo
não responder a um pedido (D5/D6 ainda por acordar).

**Prova:** `probe_client.py`, 8 servidores falsos (tabela mais abaixo).

### P5 — O servidor não validava nada do que recebia

**No M0:** um eco não precisa de olhar para os bytes. Daí o item do
`typical-problems.md` §6.3: o primeiro `->valuestring` num campo ausente é um
segfault, porque o cJSON devolve `NULL`.

**Porque é crítico:** *"um peer de outro grupo vai enviar algo inesperado — é
garantido"*. Um servidor que rebenta com uma linha mal formada derruba todos os
clientes.

**Como resolvemos:**

- Cada campo passa por **três verificações** antes de ser lido: existe, é do tipo
  certo, respeita os limites. Só então se toca em `valuestring`.
- Falhar qualquer uma → `ERROR 400` com o motivo (`invalid JSON`, `unknown type`,
  `invalid field`). O servidor **nunca rebenta e nunca fecha** por causa disto: a
  mensagem seguinte é tratada normalmente.
- O resto do programa nunca toca em cJSON: recebe uma `struct msg` em que tudo já
  foi verificado.

**Prova:** #12 (campo em falta, sem segfault), #13 (tipo errado), #14 (não-JSON),
#15 (tipo desconhecido), #16 (campos extra ignorados), #26–#30; interop 04; caso
hostil F.

### P6 — `recv()` não põe `'\0'`, e um `'\0'` a meio engana o `strlen()`

**No M0:** `typical-problems.md` §7 — "`recv()` **não** põe `\0`; nunca passar o
buffer a `printf("%s")`". O M0 já usava `%.*s` por isso.

**O caso que o M1 acrescenta:** um peer (com bug ou malicioso) pode mandar um
`'\0'` **dentro** de uma linha. Com `strlen()` o resto da linha desaparecia em
silêncio; o cJSON pararia no `'\0'` e leria só metade.

**Como resolvemos:** o comprimento viaja **sempre explícito** — `out_len` no
framing, `len` no protocolo, `cJSON_ParseWithLengthOpts` em vez de `cJSON_Parse`.
Uma linha com `'\0'` é recusada com `ERROR 400`. Nos logs, `%.*s` com o
comprimento.

**Prova:** #20 (`out_len` ≠ `strlen`), #29 (`'\0'` → 400); caso hostil F.

### P7 — UTF-8 partido entre dois `recv()`

**No M0:** registado em `typical-problems.md` §6.2. Um `á` são dois bytes
(`0xC3 0xA1`) e podem chegar em `recv()` diferentes.

**Como resolvemos — não fazendo nada, de propósito (D3):** os bytes são opacos até
haver uma linha completa. **Partir em `\n` é sempre seguro em UTF-8**, porque todos
os bytes de continuação de um caracter multibyte são ≥ `0x80` — o `0x0A` nunca
aparece *dentro* de um caracter. O bug dos acentos corrompidos só aparece quando
se interpreta como texto um buffer parcial, e nós nunca o fazemos.

**Prova:** #9 (`á` partido entre dois feeds → 4 bytes certos), #26 (os limites
contam bytes); interop 06 em modo `byte-a-byte` (`zé`, `olá` partidos a meio).

### P8 — Um `\n` dentro de uma mensagem parte-a em duas

**No M0:** a captura mostra que o `\n` vai no fio (`length 4` para `ola\n`) — é
por isso que pode ser o delimitador. O reverso: um `\n` literal **a meio** de uma
mensagem corta-a em duas, ambas inválidas.

**Como resolvemos:**

- `cJSON_PrintUnformatted()`, **nunca** `cJSON_Print()` (que indenta com `\n`).
- O cJSON escapa `"`, `\` e caracteres de controlo; e nós **recusamos caracteres
  de controlo** em `nick` e `text` (logo, sem mensagens de várias linhas no M1).
  Assim nenhum byte cresce mais de 2× ao codificar, e a maior mensagem possível
  (2164 bytes) cabe sempre numa linha — um `_Static_assert` faz a conta.

**Prova:** #18 (aspas e barras escapadas), #27 (pior caso: um só `\n`, no fim),
#31 (bytes iguais aos exemplos do slide); a mutação `cJSON_Print` falha 3 testes.

### P9 — Fugas de memória do cJSON

**Novo no M1**, mas previsto em `typical-problems.md` §7. Cada `cJSON_Parse` exige
um `cJSON_Delete`, **em todos os caminhos de erro**; cada `PrintUnformatted`
devolve memória a libertar. Num servidor que corre horas, uma fuga por mensagem
inválida acaba com a memória.

**Como resolvemos:** cada função tem **uma única saída** (`out:`) com o único
`cJSON_Delete` / `cJSON_free`; todos os erros fazem `goto out`. A `struct msg` usa
buffers fixos — o chamador não tem nada para libertar.

**Prova:** esquecer o `cJSON_Delete` ou o `cJSON_free` (mutações) é apanhado pelo
LeakSanitizer em `make test SAN=1`.

### O que o M0 já resolvia e continua garantido

| Problema | Solução (do M0) | Verificado no M1 |
|---|---|---|
| `send()` envia só parte | `send_all()` | todas as respostas passam por ele |
| `recv()==0` (FIN) | tratado como fecho, não erro | caso hostil D: meia mensagem + FIN → fecho limpo |
| RST / `SIGPIPE` | `MSG_NOSIGNAL`; `ECONNRESET` não é fatal | caso hostil C: meia mensagem + RST → servidor continua; o cliente seguinte é servido |

### O que o M1 NÃO resolve (e onde fica)

| Problema | Visto em | Fica para |
|---|---|---|
| Servidor iterativo: o 2.º cliente liga mas não é servido | M0, probe cenário 2 | **M2** |

## Arquitetura

Quatro peças sem rede, testadas à unidade, e dois `main.c` que são só canalização:

```
            servidor                                     cliente
  recv() ─bytes─▶ framing ─linhas─▶ session          teclado ─▶ ui ─struct msg─┐
                  (rxbuf)          (protocol +                                 │
                                    estado)                       protocol ◀───┘
  send_all() ◀─linha JSON── protocol ◀─resposta─┘                   │
                                                     send_all() ◀───┘
                                                     recv() ─▶ framing ─▶ protocol ─▶ ui ─▶ ecrã
```

| Peça | Ficheiros | Faz | Não faz | Explicação |
|---|---|---|---|---|
| framing | `include/framing.h`, `src/common/framing.c` | bytes ↔ linhas | não sabe o que é JSON | [`framing.md`](../framing.md) |
| protocol | `include/protocol.h`, `src/common/protocol.c` | linhas ↔ `struct msg` validada | não toca em sockets | [`protocol-layer.md`](../protocol-layer.md) |
| session | `include/session.h`, `src/server/session.c` | estado de uma ligação: linha → resposta | não toca em sockets | abaixo |
| ui | `include/ui.h`, `src/client/ui.c` | teclado → `MSG`; mensagem → texto | não toca em sockets nem no terminal | abaixo |

A separação não é estética: permite provocar **de forma determinística** os casos
que na rede acontecem ao acaso (mensagem partida a meio, duas coladas, linha
gigante). Com rede, metade deles é impossível de reproduzir à vontade.

### Ciclo de leitura (servidor e cliente)

```
n = recv(fd, chunk, RX_CHUNK)                 /* nunca mais do que RX_CHUNK */
if (n == 0) -> o outro lado fechou
if (rxbuf_feed(&rx, chunk, n) != 0) -> fechar /* inalcançável com uso correto */
for (;;) {                                    /* 0..N mensagens por recv()  */
    r = rxbuf_next_line(&rx, line, sizeof line, &len);
    if (r == RX_NEED) break;                  /* faltam bytes: voltar ao recv() */
    if (r != RX_LINE) -> ERROR + fechar       /* RX_TOOLONG (deles) / RX_FAULT (nosso) */
    tratar(line, len);
}
```

### Máquina de estados do servidor (`session`)

```
   [novo socket]
         │
         ▼
  AWAITING_NICK ──NICK válido / OK──▶ READY ──MSG──▶ CHAT ao próprio emissor
         │                              │
         │ MSG → ERROR 401              │ NICK → ERROR 400 "nick already set"
```

Função pura (`session_handle`: linha entra, resposta sai). Regras completas no topo
de `include/session.h`; as menos óbvias:

- **Erros não mudam o estado nem fecham a ligação.** A exceção é a linha demasiado
  longa (framing): `ERROR 400 "line too long"` e fecho.
- **Tipos S→C vindos de um cliente** (`OK`, `CHAT`, `ERROR`) → `400 "unexpected
  type"` em qualquer estado — não são "pedidos antes do NICK" (401).
- **O `from` do `CHAT` é sempre o nick da sessão**; um `"from"` enviado pelo
  cliente é ignorado — ninguém se faz passar por outro.
- No M1 o `CHAT` vai **só para o próprio emissor** (ainda não há lista de
  clientes). O broadcast é M2.

### Cliente (pedido-resposta)

```
ligar → NICK → 1 resposta
por cada linha do teclado: MSG → 1 resposta → mostrar
Ctrl+D → shutdown(SHUT_WR) → mostrar o que faltar → sair
```

Escolhido em vez de `poll()`/threads para manter o M1 simples e o plano do M2
(cliente com 2 threads).

- **Timeout de 5 s** na leitura (P4).
- **Vê o buffer antes do `recv()`** (P2).
- **Sem eco local:** o servidor devolve-nos o nosso `CHAT` (D5); imprimir também o
  que escrevemos duplicava a mensagem.
- **Valida antes de enviar**, com as mesmas funções do servidor
  (`proto_valid_nick`, `proto_valid_text`): nick inválido nem chega a ligar; texto
  longo ou com tab mostra `[nao enviado] <motivo>`.
- **Linha do teclado maior que o buffer:** o `fgets` parte-a e o resto viria como
  uma linha nova — o problema do framing, agora do lado do teclado. O resto é
  deitado fora até ao `\n`.
- **Tipos que ainda não conhecemos** (`EVENT`, `USERS` de um servidor mais
  avançado) são mostrados em bruto, não escondidos nem fatais.
- **Limitação:** uma mensagem que o servidor mande sem ser pedida só aparece na
  próxima leitura, e é lida *como* a resposta dessa vez — a verdadeira fica para a
  seguinte. Nada se perde, mas a ordem no ecrã pode atrasar-se (M2 resolve).

## Decisões tomadas

Registadas como **propostas** no [`PROTOCOL.md`](../PROTOCOL.md) v0.2 — só ficam
fechadas depois de acordadas com os outros grupos.

| # | Decisão | O que escolhemos | Porquê |
|---|---|---|---|
| D1 | Buffer vs. linha máxima | linha ≤ 4096 bytes incl. `\n`; `RX_CAP` = 8192 | P3 |
| D2 | Linha demasiado longa | `ERROR 400 "line too long"` e fechar, sem ressincronizar | não se sabe onde começa a mensagem seguinte |
| D3 | UTF-8 | não descodificar nem validar; bytes opacos | P7 — partir em `\n` é seguro |
| D4 | Limites | `nick` 1–32 bytes sem espaços; `text` 1–1024; `reason` ≤ 128; sem caracteres de controlo | P8; sem espaços por causa do `/msg <nick>` do M3 |
| D5 | O emissor recebe o próprio `CHAT`? | **sim** | mais simples no servidor; confirma ao utilizador que chegou mesmo ao servidor |
| D6 | `OK` ao `NICK`? | **sim** | ponto claro para o cliente passar a "ligado" |
| — | `MSG` antes de `NICK` | `ERROR 401 "nick required"` | código já proposto no `PROTOCOL.md` §5 |
| — | Segundo `NICK` | `ERROR 400 "nick already set"` | mudar de nick não existe no M1 |
| — | Tipos S→C enviados por um cliente | `ERROR 400 "unexpected type"` | nunca são válidos vindos de um cliente |
| — | Campos opcionais | `private` ausente = `false`; `reason` ausente = `""` | ser tolerante a receber |

Porque D5 e D6 importam tanto: com dois grupos a decidir ao contrário, o cliente de
um mostra mensagens **duplicadas** ou fica **à espera** de um `OK` que nunca vem —
e parece um bug de rede. O timeout do nosso cliente (P4) existe exatamente para o
caso de outro grupo ter decidido diferente.

## Notas / o que aprendi

> Como no M0: **saber dizer isto sem ler é o objetivo** — são as perguntas
> prováveis na defesa.

### 1. Porque é que tem de ser um ciclo, e não um `if`, a tirar linhas do buffer?

Porque um `recv()` pode trazer **zero, uma ou várias** mensagens (P2). Com um `if`
trata-se a primeira e a segunda fica esquecida no buffer até chegarem mais bytes —
o que pode nunca acontecer. Passa em todos os testes manuais (escreve-se uma linha
de cada vez) e falha quando duas pessoas escrevem ao mesmo tempo. E o ciclo tem
de ramificar em **três** (`RX_LINE`, `RX_NEED`, erro): com `while (r == 1)`, um
erro é indistinguível de "faltam bytes" e volta-se ao `recv()` com o buffer
envenenado.

### 2. Porque é que o buffer tem 8192 bytes e não 4096?

Porque tem de caber **o resto da leitura anterior mais um `recv()` inteiro**. O
resto é uma linha incompleta, logo sem `\n`, logo no máximo 4095 bytes; o `recv()`
traz no máximo 4096. 4095 + 4096 = 8191. O teste #22 executa esta conta, e um
`_Static_assert` impede que alguém a estrague.

### 3. O que acontece se uma linha passar o limite? Porque não se ressincroniza?

O buffer fica envenenado, o servidor responde `ERROR 400 "line too long"` e fecha.
Descartar até ao próximo `\n` parece simpático, mas não se sabe se esse `\n` é o
fim da linha gigante ou o meio de outra coisa — o resto da conversa podia ficar
desalinhado sem ninguém perceber. Fechar é previsível; adivinhar não é.

### 4. Porque é que partir em `\n` é seguro em UTF-8?

Porque todos os bytes de continuação de um caracter multibyte são ≥ `0x80`, e o
`\n` é `0x0A`. Nunca há um `0x0A` *dentro* de um caracter. Partir o *buffer* a
meio de um caracter também não faz mal, desde que nunca se interprete como texto
antes de a linha estar completa.

### 5. Que testes apanharam bugs que não esperávamos?

Os **testes de mutação**, aplicados aos nossos próprios testes. Escaparam 4 bugs
reais aos testes originais (mais um que só afeta desempenho): `>` em vez de `>=` (um peer que manda exatamente 4096 bytes
ficava à espera em vez de ser recusado), esquecer `scanned = 0` (só se via com duas
mensagens seguidas byte a byte), chaves case-insensitive, e um teste (#12) que
verificava a limpeza de `*out` num caminho em que ela nunca fazia diferença. E na
primeira versão os testes do protocolo **davam segfault** contra os stubs — um
`len - 1` com `len == 0`. Um teste tem de falhar com um relatório, nunca com um
crash.

### 6. Porque não chega o `cJSON_Parse()` normal?

Por três razões, todas sobre o que ele faz **em silêncio**: (1) lê o primeiro
objeto e ignora o resto — `{…}{…}` perderia a segunda mensagem; (2) para no
primeiro `'\0'` e lê só metade; (3) exige uma string terminada em `'\0'`, que as
nossas linhas não garantem. `cJSON_ParseWithLengthOpts` recebe o comprimento e diz
onde parou, para se verificar que não sobrou nada.

### 7. Um ACK do TCP não chega como confirmação? Para que serve o `OK`?

O M0 mostrou que não (captura, pacotes #5/#6): o **kernel** acusa a receção antes
de a **aplicação** a processar. Se o servidor rebentasse entre os dois, o cliente
recebia o ACK e nunca a resposta. O `OK` ao `NICK` (D6) e o `CHAT` devolvido ao
emissor (D5) são a confirmação **ao nível da aplicação**: provam que a mensagem foi
interpretada, não só que chegou à máquina.

### 8. Porque é que o cliente pode não ver o `ERROR "line too long"`?

É a nota 4 do M0 na prática (caso hostil B). O servidor fecha quando ainda há bytes
do cliente por ler; o kernel não pode mandar FIN ("enviei tudo") porque há dados
recebidos a ser deitados fora, e manda **RST**. Se o RST chegar antes de o cliente
ler o `ERROR`, o cliente vê só `Connection reset`. Resolver a sério exige
continuar a ler (e deitar fora) durante algum tempo antes de fechar — precisa de
timeouts, M4.

### 9. Porque é que o cliente não mostra o que o próprio utilizador escreveu?

Porque o servidor lho devolve como `CHAT` (D5). Se o cliente imprimisse também, a
mensagem aparecia duas vezes. A contrapartida: contra um servidor que decida não
devolver o `CHAT` ao emissor, o nosso cliente mostraria `[sem resposta do servidor
em 5 s]` — mais uma razão para fechar D5 com os outros grupos.
